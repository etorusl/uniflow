# UniFlow: оставшиеся функции и передача разработки

Документ для разработчика и его агента, которые продолжают UniFlow без истории исходного чата. Здесь описаны пробелы относительно целевого продукта, точки входа в код, зависимости, предлагаемый порядок работ и критерии приёмки.

**Срез репозитория: 1 ноября 2026 года, базовый коммит `36c1814` в `main`.** Статус ниже сверён с исходниками, Prisma и OpenAPI. Это не отчёт о новом прогоне приложения: при подготовке документа сервер, Docker и эмулятор не запускались. Результаты прежних проверок указаны в [основном README](README.md#проверенный-объём).

## Выполнение в ветке feat/product-completion

G1 реализован: закрытые группы, приглашения, роли, передача владения, архивирование, личная привязка предмета и административный журнал. API/веб проверены: unit, интеграционный сценарий с пятью аккаунтами и конкурентными запросами; все 14 веб-сценариев прошли на широком и мобильном экране. Android-сборка проверяется отдельно. Решения: [правила совместной работы](docs/decisions/001-collaboration.md). Нижележащий срез описывает исходную основу; дальнейшие этапы ещё не считаются выполненными.

Firebase/push и публикация на внешнем сервере отложены по указанию пользователя: ресурсы отсутствуют. Они не блокируют локальные группы, задания и файлы.

## 2. Правила, которые нужно сохранить

1. Первая версия — **веб и Android**, веб в приоритете. iOS и офлайн-синхронизация отложены.
2. Email служит логином. Обязательное подтверждение адреса не добавлять; восстановление доступа — отдельный сценарий.
3. Одна кодовая база клиента: TypeScript, React Native, Expo Router. Сервер: NestJS, модульный монолит, PostgreSQL/Prisma; worker — отдельный процесс. Замена стека и введение микросервисов не входят в оставшиеся задачи.
4. Группы закрытые. Нужны роли владельца, модератора и участника. Авторство не заменяет действующее членство.
5. Любой участник публикует задания и материалы. Автор редактирует свою публикацию; автор, модератор и владелец могут удалить её. Модератор не получает право редактировать чужой текст только из-за роли.
6. Общее групповое задание закрывают и переоткрывают **автор, модератор или владелец**, пока состоят в группе. Индивидуальное групповое задание каждый закрывает и переоткрывает только за себя.
7. Режим `INDIVIDUAL`/`SHARED` выбирают при создании группового задания и не меняют после публикации в первой версии.
8. Общая отметка группы не превращается в выполненное личное задание каждого участника. Общую и личную статистику считать отдельно.
9. Время завершения `<=` действовавшего дедлайна означает «вовремя». Снимок дедлайна при завершении сохраняется; последующее изменение срока не переписывает результат. Повторное завершение не дублирует историю.
10. Чётность расписания отсчитывается от `Semester.weekStartDate`. Повторения используют местное время и часовой пояс семестра, дедлайны — абсолютные моменты. Не заменять эти правила календарной чётностью или временем устройства.
11. Права проверяет API при каждом запросе, в том числе при чтении файла. Скрытая кнопка в интерфейсе не обеспечивает доступ.
12. Личные предметы/преподаватели не становятся общими автоматически. Группа имеет собственное название предмета; участник может отдельно связать её со своим личным предметом.

Две параллельные несовместимые миграции одной модели не нужно пытаться «склеить» редактированием уже применённых SQL-файлов.

## 4. G1 — группы, приглашения и управление участниками

### Пользовательские сценарии

Пользователь создаёт группу по предмету, становится владельцем, приглашает другого студента ссылкой или кодом. Вступивший видит список участников и доступные публикации. Владелец назначает модератора, отзывает приглашение и передаёт владение. Участник выходит из группы; после выхода новые запросы к её данным отклоняются.

### Предложение по данным

| Сущность                          | Необходимая информация и ограничения                                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `Group`                           | UUID, название, описание, название предмета, даты, состояние удаления/архивации, источник истины для владельца                       |
| `GroupMember`                     | Группа, пользователь, роль, время вступления, состояние членства/выхода; не более одного действующего членства пользователя в группе |
| `GroupInvitation`                 | Группа, создатель, хеш случайного токена/кода, истечение, отзыв, счётчик и при необходимости лимит использований                     |
| Привязка к личному предмету       | Пользователь/членство, группа, его `subjectId`; не раскрывать другим участникам личные справочники                                   |
| История административных действий | Кто и когда изменил роль, удалил участника, передал владение или отозвал приглашение; объём хранения зафиксировать                   |

Выберите один согласованный способ хранить владельца: поле группы или роль в членстве с необходимыми ограничениями. Если хранятся оба представления, их согласованность должна быть транзакционной. В каждый момент у действующей группы должен быть ровно один действующий владелец; гонка двух передач владения не должна создавать двух владельцев или ни одного.

Для приглашений используйте криптографическую случайность, хеширование секретной части и ограничение перебора кода. TTL, длина кода и лимит использований ещё не выбраны. Принятие приглашения и расходование лимита выполняйте в одной транзакции; повторный запрос уже вступившего не должен расходовать приглашение ещё раз.

### Предлагаемый API

Общий префикс всех маршрутов — `/api/v1`.

| Метод и путь                                                                     | Назначение                                                             |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `POST /groups`, `GET /groups`                                                    | Создать группу; получить свои группы с пагинацией                      |
| `GET /groups/{groupId}`, `PATCH /groups/{groupId}`                               | Прочитать/изменить разрешённые настройки группы                        |
| `POST /groups/{groupId}/invitations`                                             | Создать приглашение и один раз вернуть секретную ссылку/код            |
| `GET /groups/{groupId}/invitations`, `DELETE /groups/{groupId}/invitations/{id}` | Управлять действующими приглашениями без выдачи хешей и чужих секретов |
| `POST /groups/join`                                                              | Принять токен или код в теле запроса после аутентификации              |
| `GET /groups/{groupId}/members`                                                  | Список участников с пагинацией и минимальными данными профиля          |
| `PATCH /groups/{groupId}/members/{userId}`                                       | Изменить разрешённую роль                                              |
| `DELETE /groups/{groupId}/members/{userId}`                                      | Исключить участника с проверкой полномочий                             |
| `POST /groups/{groupId}/leave`                                                   | Выйти; владельцу сначала передать владение                             |
| `POST /groups/{groupId}/transfer-ownership`                                      | Передать владение действующему участнику                               |

Не принимайте `ownerId`, роль или идентификатор текущего пользователя из недоверенного тела запроса без серверного решения о праве. Не помещайте секрет приглашения в API-путь, который попадёт в HTTP-журнал. Ссылку вступления нужно сохранить через переход на вход/регистрацию, но не принимать приглашение автоматически до понятного действия пользователя.

### Открытые вопросы перед реализацией

- Кто создаёт/отзывает приглашения: только владелец или также модератор? Кто может исключать других модераторов?
- Может ли обычный участник видеть email других участников? Минимальный предлагаемый ответ API — ID и отображаемое имя.
- Что означает удаление/архивация группы, кто его выполняет, какой срок хранения публикаций и истории?
- Нужна ли блокировка повторного вступления исключённого пользователя по старому приглашению?
- Какие задачи и история доступны новому участнику, особенно если дедлайн прошёл до его вступления?

Эти вопросы не дают агенту разрешения ослабить уже согласованные права. Результат обсуждения запишите в архитектуре или отдельном ADR и отразите в тестах.

### Критерии готовности G1

- [ ] Два независимых аккаунта проходят создание и вступление в вебе и Android; список групп переживает повторный вход.
- [ ] Просроченное/отозванное приглашение и исчерпанный лимит не работают; конкурентное вступление не создаёт дубли.
- [ ] Участник не повышает свою роль прямым запросом. Владелец не может оставить группу без владельца.
- [ ] После выхода/исключения прямые запросы к группе отклоняются, даже если пользователь был автором публикации.
- [ ] Проверены владелец, модератор, два обычных участника, посторонний и бывший участник. Ошибки не раскрывают закрытые данные.

## 5. G2 — совместные задания и отдельная статистика

### Сценарии и данные

В режиме `INDIVIDUAL` у группы одно описание/дедлайн, но каждый студент имеет собственную отметку. В `SHARED` одна отметка видна всем; право её менять принадлежит автору, модератору и владельцу при действующем членстве.

Существующий `Task` сейчас **всегда личный**: `userId` — владелец, а `completedAt` и `deadlineAtCompletion` — его отметка. Полей `scope`, `groupId`, `mode` в базе нет. Нельзя просто добавить `groupId` и продолжить трактовать `Task.userId` как владельца всех прав группы.

Предлагаемые варианты: отдельная модель `GroupTask` с моделями отметок/истории либо обобщение `Task` с явными ограничениями области и режима. Выбор зафиксируйте до миграции. В обоих вариантах нужны:

- Группа, автор, режим, название, описание, абсолютный дедлайн, ревизия дедлайна, даты создания/изменения.
- В индивидуальном режиме — уникальная текущая отметка пары «задание — пользователь», время завершения, снимок дедлайна и история переходов.
- В общем режиме — одна текущая отметка, действовавший дедлайн и пользователь, выполнивший закрытие/переоткрытие; история не теряется при смене автора действия.
- Блокировка/условное обновление в транзакции, чтобы параллельные нажатия не дублировали отметки и события.
- Серверная проверка, что задание принадлежит указанной группе, а пользователь всё ещё состоит в ней. Авторство проверяется дополнительно, а не вместо членства.

### Предлагаемый API и интерфейс

Добавьте списки, создание, чтение, изменение, удаление, `complete`, `reopen`, `history` под `/groups/{groupId}/tasks`. Для индивидуального режима пользователь изменяет собственную отметку; произвольный `userId` в теле не должен позволять закрыть работу за другого.

В клиенте нужны экран группы, создание с выбором режима, карточка с однозначным объяснением статуса, история и отдельный блок общего прогресса. Обновите главный экран и список заданий так, чтобы личное и групповое задание различались. Контракт фильтров по группе/области нужно добавить явно; существующие фильтры личных заданий не считаются готовым объединённым списком.

### Статистика: обязательные решения

Сейчас `GET /statistics/me` считает только таблицу личных `tasks`. Нельзя заменить запрос простым соединением с участниками: это может умножить выполненные задания на число членов группы.

После G2 личные показатели должны учитывать личные задания и индивидуальные групповые отметки. Для `SHARED` нужен отдельный групповой расчёт, например `GET /groups/{groupId}/statistics`. Определите видимость индивидуальных отметок другим участникам и не отдавайте историю группы бывшим участникам через личный endpoint.

Перед расчётами примите решения для следующих случаев:

| Случай                              | Что нужно определить                                                                                        |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Пользователь вышел/был исключён     | Сохраняется ли его прошлый результат в личных числах; какие обезличенные/исторические сведения доступны ему |
| Пользователь вступил снова          | Восстанавливается ли его текущая отметка; как связана история разных периодов членства                      |
| Пользователь вступил после дедлайна | Попадает ли уже просроченное задание в его личный знаменатель и список                                      |
| Задание или группа удалены          | Удаляются ли результаты и пересчитывается ли прошлое; нужен ли tombstone/архив                              |
| Автор вышел из группы               | Кто управляет публикацией дальше; как сохраняется авторство без возврата ему доступа                        |

Эти правила пока **не согласованы**. Сохранение личного числа не должно подразумевать доступ к текущему закрытому тексту, файлам или участникам группы.

### Критерии готовности G2

- [ ] Два участника независимо выполняют `INDIVIDUAL`; отметка одного не завершает задание у другого.
- [ ] `SHARED` завершает разрешённый субъект; обычный участник не закрывает чужое общее задание прямым API-запросом.
- [ ] Повтор/гонка запросов не создают вторую отметку и событие; переоткрытие сохраняет историю.
- [ ] Изменение дедлайна после завершения не меняет «вовремя/с опозданием». Равенство дедлайну покрыто тестом.
- [ ] Общий результат не начисляется каждому участнику в личную статистику. Знаменатели и округление документированы.
- [ ] Все согласованные случаи выхода, повторного вступления и удаления проверены интеграционно; личные задания продолжают работать без изменений семантики.

## 6. F1/F2 — вложения, фотографии и материалы

### Объём

F1: прикрепить файл/фото к личному заданию, увидеть статус загрузки, открыть/скачать и удалить вложение. F2: те же действия для разрешённых групповых заданий и отдельная лента материалов группы — текстовая публикация с вложениями, которая не является заданием и не влияет на дедлайны/статистику.

### Предлагаемые модели и жизненный цикл

`Attachment`: UUID, автор загрузки, случайный внутренний ключ объекта, исходное имя, проверенный MIME, фактический размер, контрольная сумма при необходимости, состояние загрузки/готовности/удаления и даты. Нужны связи с личным заданием, групповым заданием или материалом; нельзя оставлять неограниченный произвольный `parentType` без проверки существования и прав.

`Material`: группа, автор, заголовок/текст, даты, связи вложений, выбранная политика удаления. Публиковать может любой действующий участник; редактировать — автор; удалять — автор, модератор или владелец.

Предлагаемый процесс:

1. API проверяет сессию, родительскую сущность, право добавить вложение, квоту и ограничения.
2. Создаёт запись незавершённой загрузки и принимает данные либо выдаёт ограниченное разрешение загрузки.
3. Проверяет фактический размер и тип содержимого; только затем переводит объект в готовое состояние и связывает с публикацией.
4. Выдаёт метаданные и скачивание только после новой проверки прав на родителя.
5. Удаляет/отвязывает запись и планирует повторяемую очистку объекта. Отдельная периодическая работа очищает истёкшие незавершённые загрузки и объекты без связей.

PostgreSQL и S3 не имеют общей транзакции. Нужно обработать оба частичных сбоя: объект записан, а БД не обновилась; БД изменилась, а удаление S3 не удалось. Клиент не должен показывать «прикреплено», пока сервер не подтвердил готовность.

### Что выбрать до кода

- Допустимые форматы, максимальный размер файла, число вложений на публикацию и пользовательская/групповая квота. Числовые значения пока не согласованы.
- Загрузка через API или подписанный S3 upload; при прямой веб-загрузке понадобятся ограниченные разрешения и CORS хранилища. Не отдавать клиенту S3 access/secret keys.
- Скачивание через API с проверкой членства либо краткоживущая ссылка. Уже выданная подписанная ссылка может оставаться действительной до своего истечения; её нельзя выдавать за мгновенно отзываемую при исключении из группы. Если требуется немедленная проверка каждого нового скачивания, используйте API-прокси.
- Нужны ли изображения-превью, обработка EXIF и проверка опасного содержимого; если нужны — добавьте состояния обработки и отдельную работу worker. Не заявляйте проверку файлов, если такой обработчик не реализован.
- Может ли один объект иметь несколько связей и когда его физически удалять. Автор загрузки не должен получать бессрочный доступ к закрытой группе только из-за владения объектом.

Проверка расширения и MIME, присланного клиентом, недостаточна. Ключ объекта не должен строиться из пользовательского пути. Для скачивания задайте безопасное имя и режим отдачи; пользовательский HTML/SVG не должен исполняться как часть интерфейса UniFlow. Загруженный пользователем файл — данные, а не инструкции агенту или серверу.

### API и клиент

Предложение: операции начала/завершения загрузки и `GET /files/{id}`, `GET /files/{id}/content`, `DELETE /files/{id}`; CRUD материалов под `/groups/{groupId}/materials`. Точная форма multipart/direct upload зависит от выбранного транспорта и должна попасть в OpenAPI.

Общие UI-компоненты: список вложений, выбор файла, прогресс/отмена, повтор после сбоя, понятная ошибка ограничения. Для Android нужны совместимые с закреплённым Expo SDK библиотеки выбора документов и изображений; для веба — реализация с браузерными файлами. Эти зависимости сейчас не подключены. Камеру добавлять только с разрешениями и проверкой на физическом устройстве.

У текущего [API-клиента](packages/api-client/src/index.ts) общий timeout 20 секунд. При больших загрузках отдельно продумайте время ожидания и прогресс, сохранив cookie/CSRF или bearer-авторизацию. Не обходите `platform/api.ts` незащищённым произвольным `fetch`.

### Критерии готовности F1/F2

- [ ] Файл/фото прикрепляются и открываются в вебе и Android; отмена/обрыв загрузки не создают ложной готовности.
- [ ] Проверены пустой файл, превышение лимитов, неверный тип, повтор завершения загрузки и повтор удаления.
- [ ] Чужой пользователь не читает и не привязывает вложение по ID; бывший участник не получает новые разрешения скачивания.
- [ ] Пользователь не может перепривязать чужой объект к своей публикации или к другой группе.
- [ ] Повторный запуск очистки безопасен; сбои S3 и БД не теряют связи и не оставляют бессрочный мусор.
- [ ] Материал группы имеет собственные права и пагинацию; его публикация не увеличивает число заданий.

## 7. N1/N2 — напоминания и реальный push

### Что уже подготовлено

Есть pg-boss, отдельный worker и `deadlineRevision`. Пример транзакционного добавления работы через `fromPrisma(tx)` находится в [AuthService.requestEmail()](apps/server/src/modules/auth/auth.service.ts). Сейчас в `TasksService` **нет** постановки/перепланирования напоминаний. Не следует считать наличие worker подтверждением доставки уведомлений.

### Планирование и модели

Предлагаются настройки пользователя/напоминаний, `PushSubscription`, запись запланированного напоминания и `NotificationDelivery` с историей попыток. Нужны состояние включения, смещение относительно дедлайна, получатель, устройство/браузер, транспорт, даты и причина отключения подписки.

Начните с личных заданий и затем добавьте получателей групповых. Для `INDIVIDUAL` учитывается собственная отметка студента, для `SHARED` — общий статус. Настройки по группе, тихие часы и несколько напоминаний — возможные расширения; обязательность и значения по умолчанию ещё не определены.

| Изменение                                 | Необходимое поведение                                                                    |
| ----------------------------------------- | ---------------------------------------------------------------------------------------- |
| Создано открытое задание                  | Запланировать разрешённые будущие напоминания                                            |
| Изменён абсолютный дедлайн                | Увеличить существующий `deadlineRevision`; старую отправку отменить/сделать неактуальной |
| Задание выполнено/удалено                 | Предстоящая работа не отправляет старое напоминание                                      |
| Задание переоткрыто                       | Создать новое планирование даже при неизменном дедлайне и той же ревизии                 |
| Изменены настройки/подписка               | Перепланировать или отключить затронутые доставки                                        |
| Пользователь вышел из группы              | Не отправлять ему новые закрытые сведения                                                |
| Пользователь сменил аккаунт на устройстве | Исключить уведомления предыдущего аккаунта на этом устройстве                            |

Для переоткрытия и изменения настроек одной `deadlineRevision` недостаточно. **Предложение:** отдельная версия планирования/поколение, сохраняемое атомарно, и уникальный ключ доставки с сущностью, получателем, подпиской, правилом и поколением. Не переиспользуйте ключ уже выполненной доставки для нового цикла переоткрытого задания.

Изменение бизнес-данных, версия планирования и постановка работы должны быть согласованы одной транзакцией либо проверенным transactional outbox. Перед отправкой worker заново проверяет существование, ревизию/поколение, статус, членство, настройки и подписку. Если назначенное время уже прошло, поведение нужно определить явно: пропуск или немедленная отправка в установленном окне; не отправлять пачку старых напоминаний без правила.

Реализуйте ограниченные повторы с backoff, защиту от конкурентных worker, отключение недействительных подписок и журнал конечных ошибок. Сбой после принятия сообщения внешним провайдером, но до локальной отметки нужно учитывать в модели повторов: нельзя обещать показ «ровно один раз» или доставку в точную секунду.

### Android

Согласованный SDK клиента — `expo-notifications`, доставка для Android — через FCM. Сам пакет, config plugin и Firebase-конфигурация в проект пока не добавлены.

До интеграции выберите серверный маршрут: Expo Push Service с `ExpoPushToken` или прямой FCM с нативным device token. Это разные типы токенов, их нельзя смешивать в одном поле без явного типа транспорта. Различие описано в [документации Expo о прямой отправке](https://docs.expo.dev/push-notifications/sending-notifications-custom/).

От владельца инфраструктуры понадобятся Firebase-проект с Android-приложением `com.uniflow.app`, клиентская конфигурация и серверные полномочия отправки; для варианта Expo Push Service также потребуется настройка проекта/учётных данных Expo. Наличие и доступность этих ресурсов ещё не подтверждены. Секреты сервисного аккаунта не должны попасть в `EXPO_PUBLIC_*`, Git, примеры или вывод тестов. Начните с [настройки Expo](https://docs.expo.dev/push-notifications/push-notifications-setup/), а для прямой отправки — с [FCM HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api).

Нужны разрешение пользователя, Android notification channel, регистрация/обновление/удаление токена, обработка нажатия при холодном и уже работающем приложении. Переход должен открывать нужное задание и снова проверять доступ после входа. Нельзя класть секреты или избыточные закрытые данные в текст на экране блокировки.

### Веб

Нужны отдельные Web Push подписки, VAPID-конфигурация и service worker с обработкой получения/нажатия. Android-токен не является браузерной подпиской. Service worker — требование приёма Web Push, а не реализация офлайн-синхронизации; см. [Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API).

Добавьте веб-реализацию в платформенный слой, настройте область service worker, защищённый контекст для реального размещения и доступ к статическому worker в Expo web export. Разрешение запрашивайте понятным действием, обрабатывайте отказ и неподдерживаемый браузер. Смена аккаунта и отзыв подписки должны работать отдельно от закрытия вкладки.

### Предлагаемый API и критерии готовности

Предложение: `GET/PATCH /users/me/notification-settings`, операции регистрации/отзыва `/push-subscriptions` и управления напоминаниями задания. Подписку можно изменять только в контексте текущего пользователя; токены и endpoint не должны возвращаться другим участникам или попадать в журналы.

- [ ] Планирование/перепланирование проверено с реальными PostgreSQL/pg-boss, включая rollback транзакции и перезапуск worker.
- [ ] Перенос, завершение, переоткрытие, удаление, отказ от уведомлений и выход из группы не оставляют актуальными старые отправки.
- [ ] Параллельные worker и повтор запроса не создают лишних локальных доставок; неоднозначный ответ провайдера обработан по документированному правилу.
- [ ] Реальное уведомление получено в Android development/release build и в выбранном поддерживаемом браузере; записаны среда и результат проверки.
- [ ] Отказ в разрешении, ротация токена, смена аккаунта и открытие задания из уведомления проверены.
- [ ] Локальная работа без внешних ключей явно показывает отключённую интеграцию; тестовый транспорт не засчитывается как реальный push.

Публикация в Google Play — отдельное действие при решении о распространении, не автоматическая часть подготовки.

## 9. R2 — серверное размещение, почта и эксплуатация

Сейчас есть локальный Compose только для PostgreSQL, SeaweedFS и Mailpit. Сервер/worker запускаются Node-процессами; конфигураций их production-контейнеров, reverse proxy/HTTPS и проверенного развёртывания нет. Раздел `infra/proxy` в дереве README не означает готовую конфигурацию.

### Что подготовить

1. Воспроизводимые сборки API/worker и веба, production-запуск процессов, health-check, корректное завершение и перезапуск. Для удалённого окружения убрать предположение, что `127.0.0.1` внутри разных контейнеров — одна машина.
2. Домен/HTTPS, маршрутизацию веба и `/api/v1`, ограничения запросов/загрузок, доверенные proxy-настройки. Согласовать cookie, CORS, CSRF, `WEB_ORIGIN` и встроенный в веб/Android `EXPO_PUBLIC_API_URL`.
3. Секреты отдельно от репозитория; управление доступом к PostgreSQL, S3 и почте; постоянные хранилища и миграции до переключения трафика. Не открывать локальные DB/S3/admin-порты в интернет копированием Compose.
4. Внешний SMTP и рабочий адрес отправителя. В текущих `Environment`/`MailService` нет SMTP username/password/auth: одного изменения `SMTP_HOST` для провайдера с авторизацией недостаточно. Добавить валидацию конфигурации и поддержку выбранного способа авторизации без утечки секретов. Подтверждение email при этом не вводить.
5. Единые структурированные события API/worker, связь request/job/delivery ID, метрики очереди/ошибок/возраста ожидающих работ, наблюдение за failed jobs и оповещение об отказах. Уже существующие health и HTTP request ID сохранить.
6. Backup PostgreSQL и объектов S3, сроки хранения, защита копий, регулярность и целевые RPO/RTO. Практически восстановить обе части в чистое окружение и проверить соответствие метаданных файлам.
7. Инструкцию обновления и отката: совместимость приложения со схемой, поведение worker при смене версии, безопасное применение новых миграций, действия при неуспешном релизе. Откат бинарника не считается автоматическим откатом разрушительной миграции.

Нужные внешние ресурсы: выбранный сервер/платформа, домен/DNS, SMTP, доступ к хранилищу и резервным копиям, ответственность за секреты и восстановление. Они пока не определены в репозитории. Сначала подготовьте проверяемую конфигурацию и руководство; реальная публикация требует решения о размещении и доступов.

**Готовность:** отдельное окружение разворачивается по инструкции, обновляется, наблюдается и восстанавливается из копии; проверены HTTPS-сессии, почта, объекты и worker после перезапуска. Локальный успех или наличие Dockerfile сами по себе этого не подтверждают.

Практические правила:

- Сервер — ESM/NodeNext, компилируется `tsc`; в локальных server-import сохраняйте `.js` и существующий способ генерации метаданных Nest. Не меняйте dev-компиляцию на инструмент, теряющий decorator metadata, без проверки DI/OpenAPI.
- Не импортируйте Prisma-модели в клиент. `schema.d.ts` генерируется из серверного OpenAPI, его не редактируют вручную.
- Для nullable/неоднозначных полей DTO задавайте явный `type` в Swagger-декораторе; проверяйте результат генерации, а не только компиляцию сервера.
- Глобальный префикс API — `/api/v1`, ошибки имеют форму `{ error: { code, message, requestId } }`. Новые endpoints должны пользоваться существующей валидацией/ошибками и защищённой сессией.
- Для cookie-запросов сохраняйте Origin/CSRF-защиту. Android использует bearer; не переносите браузерную сессию в `localStorage` ради простоты.
- При новой работе worker недостаточно создать очередь: нужно импортировать нужный модуль в worker-контекст и зарегистрировать обработчик. API не должен забирать доставку на себя.
- Android-проект генерируется из Expo config/plugins и не хранится в Git. Нативные настройки должны воспроизводиться после нового prebuild, а не жить только в локальном `android/`.
- `.local/`, `.env`, SDK/AVD, debug APK и базы — локальные артефакты. У другого человека их не будет; нужна установка по README и собственные ключи, а не копирование окружения автора.
- Новые зависимости подбирайте под закреплённые Node/pnpm/Expo и lockfile. Примеры из внешней документации сверяйте с установленными версиями; этот документ не предписывает автоматическое обновление стека.

## 13. Запуск, проверки и передача результата

Окружение: Node.js 24.22.1, pnpm 11.25.0; версии библиотек — в lockfile. Полный первый запуск и требования Android описаны в [README](README.md#локальная-разработка). Для одной документации поднимать Docker/эмулятор не нужно. Приведённые ниже команды уже существуют; новые production/release-команды добавляйте только после реализации и проверки.

После установленного Docker/Colima, из корня репозитория:

```sh
pnpm install --frozen-lockfile
pnpm env:init
pnpm infra:up
pnpm build:server
pnpm db:migrate
pnpm storage:init
pnpm dev
```

Веб: `http://localhost:8081`; API: `http://localhost:3000/api/v1`; локальная почта: `http://127.0.0.1:8025`. При Colima сначала выполните `colima start`. Для браузерной cookie сохраняйте согласованные localhost-адреса из `.env.example`.

Android во втором терминале:

```sh
pnpm android:emulator
pnpm dev:android          # Собрать/установить, если приложения ещё нет или изменён native config
# В последующих запусках установленного приложения:
pnpm android:open
```

После изменения моделей создайте **новую** миграцию через `pnpm db:migrate:dev` в своей локальной БД. После изменения DTO/контроллеров:

```sh
pnpm build:server
pnpm api:generate
pnpm check
pnpm test:integration
pnpm build:web
pnpm test:e2e
```

`check` не включает интеграционные и браузерные тесты или Android-сборку. Для integration/e2e нужна работающая инфраструктура; Playwright запускает worker/API/веб согласно конфигурации и может переиспользовать локальные HTTP-процессы. Нужен установленный Playwright Chromium либо `PLAYWRIGHT_CHROME_CHANNEL=chrome` для установленного Chrome. Тесты должны создавать и удалять свои данные, а не очищать все пользовательские таблицы.

После завершения своей проверки выключите оставленное вами окружение, если его не просили оставить работающим:

```sh
pnpm android:emulator:stop
pnpm dev:stop
pnpm android:build:stop
pnpm infra:down
colima stop              # Если используется Colima и VM не нужна другим проектам
```

Не заменяйте эти команды `killall java`, массовым удалением Docker volumes или сбросом рабочей БД. Gradle/Kotlin и Docker VM — отдельные процессы, которые не исчезают от закрытия вкладки браузера.

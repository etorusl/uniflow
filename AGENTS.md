# Работа с репозиторием UniFlow

## Продукт и архитектура

- Перед изменениями читать `README.md`, `docs/architecture.md` и относящийся к работе этап `docs/development-plan.md`.
- Целевые платформы первой версии: веб и Android; веб имеет приоритет для проверки сценариев. iOS и офлайн-синхронизация отложены.
- Клиент: TypeScript, React Native, Expo и Expo Router. Сервер: NestJS, PostgreSQL и Prisma. Архитектура сервера — модульный монолит с отдельным процессом фонового обработчика.
- Сохранять принятые правила предметной области. Общие задания закрывают автор, модератор или владелец при действующем членстве. Личную и общую статистику считать отдельно.
- README описывает полноценный продукт. Не использовать позиционирование учебного примера и не выдавать запланированную функцию за реализованную.
- Новые команды запуска и утверждения о готовности добавлять после фактической проверки. Использовать существующие корневые scripts и обновлять их инструкции вместе с кодом.

Текущий запрос пользователя: автоматически продолжать после исполняемой основы до используемой версии с регистрацией, предметами, расписанием, личными заданиями и статистикой. Не останавливаться на техническом каркасе; проверять сквозные сценарии и регулярно выполнять commit/push.

## Изменения и проверки

- Обновлять документацию, API-контракт и миграции вместе с соответствующим поведением.
- Проверять права на сервере, в том числе при доступе к файлам. Не экспортировать серверные модели и секреты в клиентский пакет.
- Использовать проверки по масштабу изменения. Для документации проверять ссылки и согласованность; для логики — права, границы времени, переходы состояний и работу с данными.
- При изменении клиентских интеграций проверять веб и Android. Не считать Expo Go или тестовый push-транспорт достаточным подтверждением нативной интеграции.
- Не добавлять секреты, реальные пользовательские файлы, персональные данные, сборки и локальные базы в Git.

## Коммиты и push

Пользователь явно требует регулярно коммитить и отправлять изменения в удалённый репозиторий. Это постоянное правило работы над проектом.

- Делить работу на небольшие законченные части, делать коммит после проверки каждой такой части и выполнять push, не накапливая всю разработку локально.
- Перед staging просматривать `git status` и diff; включать в коммит только относящиеся к работе файлы. Чужие изменения сохранять.
- Использовать понятное сообщение коммита о результате изменения. Не создавать коммиты, если файлы не изменялись.
- Использовать настроенный remote `origin`; сейчас это `git@github.com:etorusl/uniflow.git`. Проверять актуальные настройки перед отправкой.
- После push проверять, что удалённая ветка содержит отправленный коммит. При ошибке явно сообщать о локальном коммите и неуспешной отправке.
- Не выполнять force push, не переписывать опубликованную историю и не включать обход проверок без отдельной необходимости и явного разрешения.
- Если для доступа к GitHub или записи Git-метаданных требуется разрешение среды, запрашивать его через штатный механизм инструмента. Не считать локальный коммит успешным push.

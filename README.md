# UniFlow

UniFlow объединяет расписание, задания, дедлайны и материалы учебных групп в одном приложении. Студент планирует занятия, следит за своей нагрузкой и работает над общими заданиями вместе с участниками группы.

Целевые платформы — **веб и iOS**. Веб-версия позволяет начать работу по ссылке без установки приложения. Интерфейс адаптируется к экрану телефона и компьютера; мобильное приложение использует ту же предметную модель и серверный API.

> **Статус:** разработка начинается. В репозитории зафиксированы требования, архитектура и план реализации. Работающего приложения, команд его запуска и готовых сборок пока нет. Готовность функций отмечается в [плане разработки](docs/development-plan.md).

## Возможности

### Личный органайзер

- Регистрация по email и паролю, подтверждение почты, восстановление доступа и профиль студента.
- Личный справочник предметов и преподавателей. Преподаватели представлены именем и контактами, без отдельных аккаунтов.
- Расписание на семестр: повторяющиеся пары, чётные и нечётные недели, отмены и переносы отдельных занятий.
- Личные задания с дедлайнами, файлами и фотографиями.
- Напоминания о приближении дедлайнов и настройки уведомлений.
- Отметки о выполнении и статистика личного прогресса.

### Совместная работа

- Закрытые группы по предметам с приглашением по ссылке или коду.
- Роли владельца, модератора и участника.
- Задания и материалы, доступные участникам группы.
- Два режима выполнения групповых заданий: индивидуальный и общий.

Это описание целевого продукта. Наличие функции в списке не означает, что она уже реализована.

## Правила работы

### Группы и права доступа

Публиковать задания и материалы может любой участник группы. Автор редактирует свою публикацию; автор, модератор или владелец могут её удалить. Владелец обладает правами модератора и управляет ролями группы. Все права проверяет сервер, включая доступ к вложениям.

| Действие | Участник | Модератор | Владелец |
| --- | --- | --- | --- |
| Читать задания и материалы группы | Да | Да | Да |
| Публиковать задания и материалы | Да | Да | Да |
| Редактировать собственные публикации | Да | Да | Да |
| Удалять собственные публикации | Да | Да | Да |
| Удалять чужие публикации | Нет | Да | Да |
| Закрывать общее задание | Если автор | Да | Да |
| Управлять ролями | Нет | Нет | Да |

### Выполнение заданий

- **Личное задание:** принадлежит одному пользователю; он управляет заданием и его выполнением.
- **Групповое, индивидуальный режим:** описание и дедлайн общие, но каждый участник отмечает выполнение независимо. Отметка одного студента не закрывает задание для остальных.
- **Групповое, общий режим:** у задания один общий статус. Закрыть его могут автор, модератор или владелец группы. Общие результаты отображаются отдельно от личной статистики.

Режим выбирается при создании группового задания. Изменение режима после публикации не входит в первую версию: это сохраняет однозначность отметок и статистики.

### Расписание и время

Расписание вводится вручную и относится к определённому семестру. Повторяющиеся занятия задаются отдельно от исключений на конкретные даты. Начальная дата учебных недель задаёт отсчёт чётности; он не зависит от номера календарной недели года.

Расписание хранит время занятий и часовой пояс учебного заведения. Дедлайны хранятся как абсолютные моменты времени и отображаются в часовом поясе пользователя. Эти правила позволяют корректно работать при поездках и смене часового пояса.

### Статистика

Личная статистика учитывает личные задания и индивидуальное выполнение групповых заданий:

- **выполнено вовремя** — завершено не позднее дедлайна;
- **выполнено с опозданием** — завершено после дедлайна;
- **просрочено** — дедлайн прошёл, а выполнение ещё не отмечено.

Дата выполнения сохраняется. Общие задания группы имеют отдельные показатели и не добавляют каждому участнику личное выполненное задание. Подробные правила переходов и расчётов описаны в [архитектуре](docs/architecture.md).

### Соединение и уведомления

Первая версия работает **при наличии соединения с сервером**. Офлайн-редактирование и последующая синхронизация отложены; локальная база данных и очередь несинхронизированных изменений сейчас не внедряются. Сбой сохранения явно показывается пользователю.

Уведомления о дедлайнах формируются на сервере. Для iOS используется `expo-notifications` с доставкой через APNs; веб использует отдельную интеграцию Web Push. Пользователь разрешает уведомления и настраивает напоминания. Повторные попытки отправки не должны создавать повторные напоминания, а перенос дедлайна должен обновлять запланированную отправку.

Реальная доставка push требует интернета и внешней инфраструктуры платформ. Для APNs нужны соответствующие учётные данные Apple Developer Program. Локальная разработка остальной системы не зависит от публикации в App Store.

## Технологии

| Область | Выбор |
| --- | --- |
| Язык клиента и сервера | TypeScript |
| Клиент | React Native, Expo, Expo Router |
| Веб | React Native Web, адаптивные экраны |
| Сервер | NestJS, модульный монолит |
| API | REST, OpenAPI, генерируемый TypeScript-клиент |
| Основные данные | PostgreSQL |
| Доступ к данным и миграции | Prisma |
| Фоновые задачи | pg-boss поверх PostgreSQL, отдельный процесс обработчика |
| Файлы | Закрытое объектное хранилище с S3 API; локально SeaweedFS |
| Почта | SMTP; локально Mailpit |
| Зависимости | pnpm workspace |
| Локальная инфраструктура | Docker Compose |
| Проверки | TypeScript, ESLint, форматирование, модульные и интеграционные тесты, Playwright для веб-сценариев |

Клиент и сервер развиваются в одном репозитории. PostgreSQL хранит пользователей, права, расписание и задания, объектное хранилище — содержимое вложений. `pg-boss` использует PostgreSQL, поэтому отдельный Redis для очереди не требуется.

API и обработчик фоновых задач собираются из одного серверного проекта, но запускаются разными процессами. Изменение языка серверной части не предполагается; мобильный и веб-клиенты зависят от контракта API, а не от внутренних моделей Prisma.

Точные версии Node.js, pnpm, Expo и контейнеров будут закреплены при создании исполняемого каркаса после проверки совместимости. Воспроизводимость обеспечивается зафиксированными версиями, lockfile и миграциями.

```text

├── apps/
│   ├── client/                 # Общее приложение Expo: веб и iOS
│   │   └── src/
│   │       ├── app/            # Маршруты Expo Router
│   │       ├── features/       # Экраны и логика пользовательских функций

│           ├── modules/        # Предметные модули NestJS
│           ├── infrastructure/ # БД, очередь, почта и объектное хранилище
│           └── common/         # Общие серверные механизмы
├── packages/
│   ├── api-client/            # Клиент и типы из OpenAPI
│   └── config/                # Общие настройки инструментов
├── infra/
│   ├── compose/               # Локальная инфраструктура
│   └── proxy/                 # Маршрутизация и HTTPS
├── tests/

├── docs/
│   ├── architecture.md        # Модули, данные, права и эксплуатация

```

Это согласованная структура. Исполняемые точки входа, конфигурации workspace и команды добавляются на первом этапе реализации. Пустые каталоги каркаса обозначаются `.gitkeep`.

## Локальная разработка

Планируемое окружение:

- Node.js совместимой LTS-версии и pnpm для клиента и сервера.
- Docker с Docker Compose для PostgreSQL, S3-совместимого хранилища и Mailpit.
- Браузер для разработки и проверки веб-версии.
- macOS, Xcode и установленный iOS Simulator для локальной сборки и проверки iOS.

Веб — первый канал проверки пользовательских сценариев. iOS собирается и проверяется уже с первого этапа, чтобы платформенные различия выявлялись по мере разработки. Для нативных интеграций используется собственная development build; Expo Go не считается проверкой готовности мобильной версии.

Пока исполняемый каркас не создан, команды установки и запуска намеренно не приводятся. Первый этап добавит корневые команды запуска, `.env.example`, локальную инфраструктуру и проверенную инструкцию настройки. Пароли, ключи, пользовательские файлы и реальные данные не включаются в Git.

## План выпуска

1. **Основа:** workspace, сервер, веб и iOS, локальные сервисы, API-контракт и CI.
2. **Учётная запись:** регистрация, подтверждение email, вход, восстановление доступа и профиль.
3. **Расписание:** предметы, преподаватели, семестры, повторения и исключения.
4. **Личные задания:** дедлайны, выполнение и статистика.
5. **Группы:** приглашения, роли и два режима выполнения заданий.
6. **Материалы:** закрытые вложения, фотографии и общие публикации.
7. **Уведомления:** настройки, планирование, реальные iOS и веб-push.
8. **Подготовка выпуска:** сквозные проверки, эксплуатационная документация, резервное копирование и проверка развёртывания.

Каждый этап заканчивается проверяемым результатом, коммитом и push. Подробные зависимости и критерии готовности — в [плане разработки](docs/development-plan.md).

## Развёртывание

Архитектура рассчитана на локальную разработку с последующим размещением на сервере. Для развёртывания потребуются веб-сборка, API, фоновый обработчик, PostgreSQL, объектное хранилище, HTTPS, SMTP и учётные данные push-провайдеров. Публикация приложения для iOS выполняется отдельно от развёртывания серверной части.

Перед первым размещением должны быть проверены миграции, права доступа, резервное копирование и восстановление, health-проверки, журналы ошибок и доставка уведомлений. Готовые инструкции развёртывания появятся вместе с проверенными конфигурациями; размещение пока не выполнено.

## Работа с изменениями

Удалённый репозиторий: [etorusl/uniflow](https://github.com/etorusl/uniflow).

- Делить работу на небольшие законченные изменения и регулярно делать коммиты.
- Перед коммитом проверять diff и выполнять проверки, относящиеся к изменению.
- Отправлять каждый завершённый и проверенный этап в удалённый репозиторий, не откладывая push до конца всей разработки.
- Обновлять документацию при изменении поведения, архитектуры или команд запуска.
- Сообщать о неуспешном push; локальный коммит сам по себе не означает сохранение в удалённом репозитории.
